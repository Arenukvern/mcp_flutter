# MCP Registry publish runbook

The official [MCP Registry](https://registry.modelcontextprotocol.io) entry
(`io.github.Arenukvern/flutter-mcp-toolkit`) is published by dispatching
`publish_mcp_registry.yml` (Actions → Run workflow on **`main`** with the
`release_tag` input), which builds the OCI image, pushes it to GHCR, and
publishes `mcp_server_dart/server.json` to the registry. `server.json` lists
two packages in order: the **OCI image** (first) and the **MCPB bundle**
(`flutter-mcp-toolkit.mcpb`, second) with a publish-time `fileSha256`. (It
used to auto-trigger from `pub_publish.yml` on `v*` tags; pub packages now
release per-tag via dart_changesets, so the registry publish is an explicit
dispatch after the pub train lands — 2026-11-21.)

This pipeline failed four times before its first green run. Every failure mode
is now covered by a local gate — see
[ADR 0013](/decisions/0013_mcp_registry_publish_hardening.mdx) for the full
post-mortem.

## After-release recovery (v7.1.0+ partial train)

Use when the `v*` tag and GitHub Release exist, pub.dev already has all packages, but
downstream automation failed (release binaries and/or MCP Registry OCI publish).
**Do not** re-tag, republish pub.dev, or merge a Release PR again for the same version.

| Failure | Recovery |
|---------|----------|
| Missing `flutter_mcp_*` tarballs or `checksums.txt` | On `main`, **Actions → Release → Run workflow** with `release_tag` (e.g. `v7.1.0`). See [release_binary_recovery](/contributing/release_binary_recovery). |
| Missing `flutter-mcp-toolkit.mcpb` (tarballs + `checksums.txt` present) | The registry publish fails closed before publishing (`assert_mcp_registry_release_assets.sh` gate). Re-run the **Release** workflow on `main` with `release_tag` — the publish step gap-fills only the missing assets — then re-dispatch **Publish MCP Registry server**. The bundle hash is reproducible (normalized timestamps), so the rerun matches. |
| Invalid `flutter-mcp-toolkit.mcpb` with **all four** expected assets present | The Release rerun is **blocked** by `check_release_assets_conflict.sh` (full conflict) before any upload — do not assume a rerun replaces the bundle. Recovery options from the guard message: (a) delete the existing `flutter-mcp-toolkit.mcpb` asset (and its `checksums.txt` line) on the GitHub release page, then re-run Release to upload a corrected bundle, or (b) cut a new tag. After either, re-dispatch **Publish MCP Registry server**. |
| MCP Registry image / `server.json` publish | On **`main`** (after tooling fixes are merged), **Actions → Publish MCP Registry server → Run workflow** with `release_tag` (e.g. `v7.1.0`). The workflow uses **tooling from `main`** (fixed `Dockerfile.registry`) and **server code from the tag**; `server.json` (registry metadata) also comes from **`main`**, version-synced to the release — a tag cut before a metadata change must not republish stale metadata for an immutable Registry version. |

Dispatch `publish_mcp_registry.yml` on **`main`** with the `release_tag` input — never from
the tag ref (the tag tree may still carry a broken Dockerfile).

## Recovery when pub.dev publish failed mid-train

The pub train runs one
[dart_changesets publish](https://github.com/Arenukvern/mcp_flutter/blob/main/.github/workflows/dart_changesets_publish.yml)
workflow **per package tag**, dispatched when the version PR merges; each run
waits for its same-train dependency floors on pub.dev before uploading. The
registry publish is never auto-triggered — it is always an explicit dispatch
(see above). If some tags' publish runs failed after others uploaded
(transient pub.dev errors, a red preflight on one leg):

1. **workflow_dispatch** [dart_changesets publish](https://github.com/Arenukvern/mcp_flutter/blob/main/.github/workflows/dart_changesets_publish.yml) on `main` for each failed tag with **`execute` checked** (`--skip-existing` skips versions already on pub.dev; the engine's publish-tag re-checks dependency floors, waiting up to 15 minutes — `dependency-wait-minutes` on the reusable workflow tunes it). Re-pushing an unchanged tag fires no workflows — dispatch is the only re-run path.
2. When all intended packages are on pub.dev, run [Publish MCP Registry server](https://github.com/Arenukvern/mcp_flutter/blob/main/.github/workflows/publish_mcp_registry.yml) via **workflow_dispatch** on **`main`** with `release_tag` set to the root `v*` tag.

## Pre-flight gates (run before cutting a release)

```bash
make check-contracts                          # includes check_mcp_registry.sh
steward action run fmt.check.mcp-registry     # same check via Steward
```

The `check_mcp_registry.sh` contract asserts:

- `server.json` name, description bounds, and version match root `VERSION`.
- The OCI package identifier is exactly
  `ghcr.io/arenukvern/flutter-mcp-toolkit:<VERSION>` and carries **no**
  `registryBaseUrl` field (the Registry rejects it).
- The Dockerfile compiles `bin/flutter_mcp_toolkit_server.dart`, installs a
  **sha256-pinned** Flutter stable linux SDK matching CI (`tool/contracts/flutter_sdk_pin.env`),
  and never runs `--enforce-lockfile` (SDK-bundled pins differ per host platform).
- PR/push CI (`.github/workflows/mcp_registry_dockerfile.yml`) builds
  `Dockerfile.registry` for `linux/amd64` without pushing when registry paths change.
- The smoke workflow resolves siblings from **pub.dev** when the pinned train is
  already published; otherwise it builds from a **temporary** context with path
  overrides (version PRs before the pub train lands on pub.dev). Production publish still
  uses `context: .` with **hosted-only** resolution (after pub.dev).
- `assert_mcp_registry_no_pubspec_overrides.sh` runs immediately before the
  production OCI build and fails if `mcp_server_dart/pubspec_overrides.yaml`
  exists in the workspace.
- **MCPB fail-closed gate:** before any publish, the workflow downloads
  `flutter-mcp-toolkit.mcpb` + `checksums.txt` from the release and
  `assert_mcp_registry_release_assets.sh` verifies the bundle exists, its
  sha256 matches `checksums.txt`, both platform binaries
  (`server/darwin-arm64/…`, `server/linux-x64/…`) are inside, and the bundled
  manifest version equals the release version. A failure aborts the job —
  registry versions are immutable, so an incomplete release is never
  published.
- **`fileSha256` injection:** after the gate passes, the workflow injects the
  verified bundle hash into the `mcpb` package of `server.json` (the
  checked-in file intentionally carries no hash) and `mcp-publisher validate`
  sees the final manifest.
- The MCPB bundle itself is packed by the Release workflow's `mcpb` job via
  `tool/release/pack_mcpb_bundle.sh` (official `@anthropic-ai/mcpb` CLI,
  version-pinned in `MCPB_CLI_VERSION`), and its layout is pinned to the
  release matrix by `tool/contracts/test_mcpb_manifest_matrix.sh`
  (`make check-contracts`).
- **Train race:** per-tag publish runs are dispatched concurrently, but
  pub.dev validates dependency constraints at upload time. The engine's
  `publish-tag` therefore waits (default 15 minutes, progress logged per
  poll, `dependency-wait-minutes` input to tune) until the package's
  same-train dependency floors are exposed on pub.dev — the train converges
  regardless of dispatch order, uniformly for every consumer repo. Preflight
  (`execute=false`) skips the publish itself but still exercises the wait.
- Offline contract coverage uses `MCP_REGISTRY_PUB_API_BASE` pointed at
  `tool/contracts/fixtures/mcp_registry_pub_api/`; smoke CI uses live pub.dev
  (`python3` + PyYAML + `curl` on ubuntu-latest).
- pub.dev publication still triggers the dependent registry publication.

## Manual validation of server.json against the live registry

```bash
./mcp-publisher validate mcp_server_dart/server.json
```

Install the pinned publisher binary as the workflow does (see
`publish_mcp_registry.yml` for the pinned version and SHA256).

## Local end-to-end image build

```bash
docker build --platform linux/amd64 \
  -f mcp_server_dart/Dockerfile.registry -t fmtk-registry-test .
docker run --rm fmtk-registry-test --version   # should print VERSION
```

Always test on `linux/amd64` — that is what CI uses, and dependency resolution
differs per host platform.

## Known constraints (do not "fix" these back)

1. **No lockfile enforcement in Docker.** A host-generated `pubspec.lock`
   breaks cross-platform builds because Flutter SDK-bundled pins differ between
   arm64 and amd64. Reproducibility comes from the pinned base-image tag.
2. **Build from repo root.** `mcp_server_dart` depends on workspace siblings
   (`packages/*`, `mcp_toolkit`) that are not on pub.dev; a bare
   `mcp_server_dart/` context cannot resolve.
3. **Flutter SDK base image required.** `intentcall_platform` requires the
   Flutter SDK; a pure `dart:SDK` image fails at resolution.

If any of these need to change, update [ADR 0013](/decisions/0013_mcp_registry_publish_hardening) first.
