# Recover missing GitHub Release binaries

Use when a tagged release exists but [`release.yml`](https://github.com/Arenukvern/mcp_flutter/blob/main/.github/workflows/release.yml) failed before attaching `flutter_mcp_<version>_<triple>.tar.gz` and `checksums.txt` (for example after a GitHub hosted macOS arm64 runner shortage that cancels `macos-15` build jobs with **zero steps**).

## Preconditions

- The git tag (for example `v7.0.2`) and GitHub Release already exist from release-please.
- The release must have **no** expected tarballs or `checksums.txt` yet (all three names absent). A **partially** populated release (for example only `linux-x64` uploaded) still fails the conflict guard and does not upload missing assets — delete the existing expected assets in the GitHub Release UI, then re-dispatch.
- Recovery does **not** create, move, or delete tags and does **not** republish pub.dev or MCP Registry packages.
- **MCP Registry smoke CI** on release-please PRs is unrelated to tarball recovery: smoke builds use ephemeral sibling path overrides when pub.dev does not yet expose the bumped train; production registry publish remains hosted-only after `pub_publish`.

## How the workflow is wired

| Checkout | Purpose |
|----------|---------|
| `_tooling` at `${{ github.sha }}` | Trusted helper scripts from the workflow commit (`persist-credentials: false`) |
| `release-src` at `refs/tags/<tag>` | Immutable product source used to compile binaries |

Build uses **tooling** scripts against **release-src** (`RELEASE_ROOT`). Historical tags (for example `v7.0.2`) may lack newer helpers; dispatch recovery still works because helpers come from `_tooling`.

## Automatic runner-shortage retry

[`release_runner_retry.yml`](https://github.com/Arenukvern/mcp_flutter/blob/main/.github/workflows/release_runner_retry.yml) runs on **Release** `workflow_run` completion when the triggering repo is canonical (not a fork). It inspects failed/cancelled jobs and **only** re-runs jobs that look like hosted-runner acquisition failures:

- job cancelled with **zero steps** and `runner_id: 0`, or
- a check annotation containing GitHub’s “not acquired by a Runner of type hosted” message.

It refuses to rerun when any job failed a real build/test step, backs off a few minutes based on `run_attempt`, and caps at **three** attempts. Each decision is written to the job summary.

## Manual recovery (maintainers)

1. **Re-run failed jobs** on the Release workflow run when only the macOS matrix job was cancelled and the linux artifact already succeeded (safe after the retry workflow hits its cap).
2. Or open **Actions → Release → Run workflow** on `main` (after runner/dispatch fix is merged).
3. `release_tag`: existing tag (for example `v7.0.2`).
4. The run checks out `release-src`, records `release_sha`, and uploads to that tag via explicit `tag_name` (`publish_release_assets.sh` uses `gh release upload --clobber` for idempotent recovery).

**Not verified in CI:** a full end-to-end dispatch against `v7.0.2` until a maintainer runs it post-merge.

## Changelog convention

Ship runner/dispatch hardening via conventional `fix(release):` on `main`; release-please aggregates into the next version — do not add a stranded `## [Unreleased]` block for recovery-only workflow edits.
